Every engine starts as a window that opens and closes. Ponko's opened on
2 November. By the end of the next day it was simulating a million units
fighting over a map, in Rust, C and C++, in a browser, and under the control of
an AI agent.

This is how the base of the engine came together, and the numbers it reached.

## The loop, then the sprites

The first pieces were the ones every game needs before anything else: a
window, a game loop and input. Then a sprite renderer on
[wgpu](https://wgpu.rs/), which draws with Vulkan, Metal, DirectX and
WebGPU from the same code. Sprites are drawn in instanced batches: one draw
call for thousands of sprites that share an image.

The shape of a game was settled here too. A game is a closure that sets
things up and returns the closure that runs every frame:

```rust title="src/main.rs"
use ponko::prelude::*;

fn main() {
    Game::new("My Game", 800, 600).run(|ctx| {
        let crab = ctx.load_texture("crab.png");
        let mut pos = vec2(400.0, 300.0);

        move |ctx: &mut Ctx| {
            if ctx.key_down(Key::Right) { pos.x += 200.0 * ctx.dt(); }
            if ctx.key_down(Key::Left)  { pos.x -= 200.0 * ctx.dt(); }
            ctx.draw(&crab, pos);
        }
    });
}
```

## Our own ECS

Plain variables are enough for a small game. A big one wants an entity
component system, where things in the world are rows of components and
systems are functions over them.

Before writing one, we measured. A spike compared an archetype ECS of our
own against [bevy_ecs](https://crates.io/crates/bevy_ecs) and
[hecs](https://crates.io/crates/hecs) on the same workload. Ours iterated
fastest, so `ponko_ecs` became the engine's ECS: generational entity ids,
queries, commands, resources, and components registered at runtime, so C and
C++ can define their own.

Then `par_for_each`, which splits a query's work across every core through
[rayon](https://crates.io/crates/rayon). Writing a system for all cores is
the same as writing it for one:

```rust
ctx.world.query::<(&mut Transform2D, &Speed)>().par_for_each(|(t, speed)| {
    t.position.x += speed.0 * dt;
});
```

## Simulations at scale

Games with huge crowds need more than a fast loop, so the next pieces were the
tools for those:

- **A fixed-rate simulation clock** that can pause, step one tick, or run at
  1 to 64 times speed, with systems that run every N ticks.
- **Headless runs**, with no window and no GPU, for servers, tests and long
  batch runs.
- **Spatial grids** for radius, rectangle and nearest-neighbour queries, and
  spatial sorting, so entities that are neighbours on the map are neighbours
  in memory.
- **Flow-field pathfinding**, where one field steers every unit heading to the
  same goal.
- **Determinism**: randomness seeded per seed, tick, system and entity, the
  same with parallel queries, and a whole-world save and load that keeps
  entity ids.

Three demos push these at a million entities each:

On the drawing side, a million moving sprites hold 120 frames a second, the
display's cap.

## Everything else on day two

By the end of 3 November the engine also had:

- **A C API and a header-only C++17 wrapper** that cover nearly the whole
  engine. The battle demo was rewritten in C++ and runs at the same speed as
  the Rust one.
- **Web builds.** The same game runs in a browser on WebGPU or WebGL2.
- **2D physics** through [Rapier](https://rapier.rs/), with an option for
  bit-identical results on every platform.
- **Lockstep multiplayer** for 2 to 8 players over UDP or Steam's relays,
  with desync checks that name the components that differ.
- **Fast iteration**: hot reload of images, sounds, fonts and data files, and
  hot-patching of game code while it runs.
- **A runtime inspector** on the <kbd>`</kbd> key, and an MCP server that lets
  AI agents start, inspect and drive a game. That one has
  [its own post](/blog/agents-play-the-game/).

Ponko's first commit opened a window and closed it again. That was on
2 November. By the end of the 3rd it could simulate a million units fighting
over a map, from Rust, C or C++, in a browser, with an AI agent driving it.

Here's the order things went in, and what we measured along the way.

## The loop, then the sprites

We started with the stuff every game needs first: a window, a game loop and
input. Then came a sprite renderer on [wgpu](https://wgpu.rs/), which gets us
Vulkan, Metal, DirectX and WebGPU from one codebase. Sprites that share an
image are drawn in instanced batches, so thousands of them cost one draw call.

We also settled on what a game looks like in code. You pass a closure that
does the setup, and it returns another closure that runs every frame:

```rust title="src/main.rs"
use ponko::prelude::*;

fn main() {
    Game::new("My Game", 800, 600).run(|ctx| {
        let crab = ctx.load_texture("crab.png");
        let mut pos = vec2(400.0, 300.0);

        move |ctx: &mut Ctx| {
            if ctx.key_down(Key::Right) { pos.x += 200.0 * ctx.dt(); }
            if ctx.key_down(Key::Left)  { pos.x -= 200.0 * ctx.dt(); }
            ctx.draw(&crab, pos);
        }
    });
}
```

## Writing our own ECS

For a small game, plain variables like `pos` above are fine. Bigger games
usually want an entity component system: entities are rows of components,
and systems are functions that run over them.

We didn't want to write one without a reason, so we first built a small
archetype ECS and benchmarked it against
[bevy_ecs](https://crates.io/crates/bevy_ecs) and
[hecs](https://crates.io/crates/hecs) on the same workload. Ours came out
fastest at iteration, so it stayed and became `ponko_ecs`. It has
generational entity ids, queries, commands and resources. Components can be
registered at runtime, which is what lets C and C++ code define its own.

Next was `par_for_each`, which spreads a query over all your cores with
[rayon](https://crates.io/crates/rayon). The code looks the same as the
single-threaded version:

```rust
ctx.world.query::<(&mut Transform2D, &Speed)>().par_for_each(|(t, speed)| {
    t.position.x += speed.0 * dt;
});
```

## Big simulations

A fast loop isn't enough for games with huge crowds, so we added the tools
those games end up needing:

- A fixed-rate simulation clock. It can pause, step a single tick, or run
  anywhere from 1x to 64x, and systems can run every N ticks.
- Headless runs with no window and no GPU, for servers, tests and long batch
  jobs.
- Spatial grids for radius, rectangle and nearest-neighbour queries. Entities
  are also sorted by position, so neighbours on the map sit next to each other
  in memory.
- Flow-field pathfinding. One field steers every unit that's heading to the
  same goal.
- Determinism. Random numbers are seeded per seed, tick, system and entity,
  and stay the same with parallel queries. You can also save and load the
  whole world with entity ids intact.

We wrote three demos that run a million entities each:

as high as the display goes.

## The rest of day two

A lot more landed on 3 November:

- A C API and a header-only C++17 wrapper that cover almost all of the
  engine. We ported the battle demo to C++ and it runs as fast as the Rust
  one.
- Web builds. The same game runs in the browser on WebGPU or WebGL2.
- 2D physics with [Rapier](https://rapier.rs/), including an option for
  bit-identical results on every platform.
- Lockstep multiplayer for 2 to 8 players over UDP or Steam's relays. When
  clients desync, the check tells you which components differ.
- Hot reload for images, sounds, fonts and data files, and hot-patching of
  game code while it's running.
- A runtime inspector on the <kbd>`</kbd> key, and an MCP server so AI agents
  can start, inspect and drive a game. That one got
  [its own post](/blog/agents-play-the-game/).

After that, we started on 3D.

In the first week we mostly added features: sprites, an ECS, 3D, physics,
animation. This week was more about making that work well in an actual game.
Here's what changed.

## The name and the version

The engine was renamed to **Ponko** on 8 November, and its packages restarted
at 0.0.1. We picked a low number on purpose. The API still changes, and when
it does, the changelog says so.

## Phases and plugins

Systems now run in explicit phases. Each system says when it should run:
before or after the physics step, or during drawing.

```rust
Game::new("Drive", 1280, 720)
    .add(Phase::BeforePhysics, steer) // the step below sees this tick's input
    .physics3d(vec3(0.0, -9.81, 0.0))
    .add(Phase::Draw, draw_hud)
    .run();
```

Features are packaged as plugins. A plugin adds its systems to their phases
and can run some setup once at startup. The `coin_dash` example, a complete
game, is put together out of plugins.

## Error handling

There's now a single error type, `ponko::Error`. It has a kind you can match
on, the asset path, and a readable message. Every loading call now has a
`try_` version that returns it, for games that want to show an error instead
of crashing:

```rust
match ctx.gfx.try_load_texture("skins/gold.png") {
    Ok(skin) => player.skin = skin,
    Err(e) if e.kind() == ErrorKind::NotFound => {} // keep the default
    Err(e) => eprintln!("{e}"),
}
```

Handles are now checked by generation too. If you hold on to an old mesh or
buffer handle after its slot was reused, it won't point at the new resource.

Input actions have ids now as well. Look up the name once with
`ctx.input.action_id("jump")` and use the id every frame afterwards, without
a string lookup each time.

## Better queries

- Typed filters: `With<T>`, `Without<T>` and `Or<(With<A>, With<B>)>` through
  `query.filter::<F>()`. The same filters are available from C and C++.
- Change detection. `Changed<T>` and `Added<T>` only match entities whose
  component was changed or added since the system last ran.
- Parallel queries now spread work over all cores even when it's split
  across many small archetypes. Before, each archetype had to finish before
  the next one started. With 4,096 archetypes and heavy per-entity work, it's
  about 9x faster on 14 cores.

## Running systems in parallel

There's an optional scheduler you turn on with
`Game::parallel_systems(true)`. Systems that declare what they read and
write can then run at the same time, as long as they don't overlap. If you
don't turn it on, nothing changes.

## Asset streaming

- Uploads have a budget. Assets go to the GPU a bit at a time each frame, in
  the order they were requested. A texture starts out as a small placeholder
  and doubles in resolution with each upload.
- Residency budgets. Once a memory budget is exceeded, the least recently
  used textures go back to their placeholder and stream in again when
  they're needed.
- GPU tiers. `PONKO_GPU_TIER=webgl2` or `baseline` opens the GPU with that
  tier's limits, so you can check on a fast machine what a slow one will get.
- Broken shaders no longer stop the game. If a shader fails to compile, or
  the GPU rejects it, the engine keeps using the previous version or a
  placeholder and reports the error with its line and column. Save a fix and
  it loads.

## Less work per frame

The 3D renderer now only updates what changed since the last frame. It
tracks which models changed, and only re-culls when a model or the camera
moves.

<Stats>
  <Stat value="25">KiB uploaded per frame at 100,000 models, down from 789</Stat>
  <Stat value="0.26">ms of GPU culling for 4,096 batches, down from 7.8</Stat>
</Stats>

The culling number is new as of today. Big static batches are now culled on
the GPU in a single compute dispatch, where before it took one per batch and
view. For the same scene, the renderer's CPU time dropped from 9.4 ms to
1.1 ms.

## A complete game

`coin_dash` is our example of a whole game, as opposed to a demo of one
feature. It has menus, a settings screen where you can rebind keys and
gamepad buttons, saved progress, and sound effects generated in code. It's
packaged with its licences and tested on Linux, macOS, Windows and the web.
The guide goes through it in
[A complete game, packaged](/guide/packaging.html).

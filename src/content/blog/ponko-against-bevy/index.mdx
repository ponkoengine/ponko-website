Ponko's home page says it draws 100,000 moving sprites in 1.10 ms, where
Bevy takes 11.6 ms. A number like that should make you suspicious. This post
shows where it comes from: sixteen workloads, each written once for Ponko and
once for [Bevy](https://bevy.org) 0.20.1, and timed the same way on two
machines.

It also shows the row Bevy wins, the settings that nearly halve Bevy's sprite
time, and what a table like this can't tell you. I'll start there, because
it's the part an engine's own blog is least likely to lead with.

## Where Bevy Is Ahead

**Skinned characters on Vulkan.** On a Windows desktop with a Radeon RX Vega,
Bevy draws 1,000 animated characters with a sun shadow in 8.35 ms a frame.
Ponko takes 8.72 ms. The ranges of the three runs don't overlap, so this is
a real difference and not noise. Ponko is ahead on the same machine with
DirectX 12, and on a MacBook with Metal, but four days before that
measurement Bevy won on the MacBook too. More on that row
[below](#the-row-that-changed-sides).

**Pipelined rendering.** Bevy can simulate one frame while it renders the one
before, on another thread. Ponko has no pipelined renderer: it simulates,
then renders, one after the other. The first table below turns pipelining
off for Bevy so that both engines do the same work in the same order. The
second table turns it back on, and Bevy's sprite frame falls from 11.6 to
6.74 ms.

**Linking.** With Bevy's `dynamic_linking` feature, its debug link step takes
0.08 s against Ponko's 0.12 s.

**Everything a stopwatch can't see.** Bevy has a far larger community, a
plugin ecosystem, released games and several maintainers. Ponko has one
maintainer and no released games. None of that is in a table of
milliseconds, and for most projects it matters more.
[Ponko vs Bevy vs Unity](/guide/comparison.html) goes through it.

## How It Was Measured

Each workload exists twice: as an ordinary Ponko game and as an ordinary
Bevy app. The Bevy side uses the API Bevy's own documentation recommends for
the job, and the benchmark's
[README](https://github.com/ponkoengine/ponko/blob/main/bench/compare/README.md)
names that API for every workload, with links, and lists what is and isn't
the same on both sides.

One script builds both sides in release and runs everything:

- Every workload runs three times per engine, one process at a time. The
  engine that goes first changes from run to run.
- Before each run the script waits for the machine's 1-minute load to drop
  under 3, and records the load next to the result.
- One run's number is the median frame (or tick) of 300, after 60 warm-up
  frames. The tables give the median of the three runs, with their range in
  brackets.
- The rows that draw render into an offscreen 1280 × 720 target, and every
  frame waits for the GPU to finish. Nothing is capped by a display.
- Two results are "within noise" when their ranges overlap.

Bevy is pinned to 0.20.1 in its own crate with its own lock file, so it is
never part of Ponko's build. Both physics rows use the same rapier 0.36.1.

The first machine is a MacBook Pro with an Apple M4 Max (10 performance and
4 efficiency cores, 36 GB), macOS 27.2.1, Metal, rustc 1.100.0. Most rows
were measured on 22 November 2026. The two 3D rows were measured again on
26 November, after a change to skinning.

Three of these need a note.

**The sprite rows are the widest gap, and tints make it wider.** Bevy 0.20
draws each `Sprite` as a 2D mesh with a material, and equal sprites share
one material. One color is its fast path. Give every sprite its own tint and
every sprite gets its own material: Bevy's frame grows from 11.6 to 44.8 ms.
Ponko batches tinted and untinted sprites the same way, so its two rows are
the same. Neither engine multisamples these rows.

**Time to first frame is a warm launch.** It counts one launch after a
warm-up launch, so the file cache and the driver's shader cache are warm for
both. The very first launch after a build took Ponko 487 ms.

**Pipelining is off for Bevy here**, as said above. The next table has it on.

## Both Engines Tuned

A careful game doesn't ship with the defaults, so a second table measures
each engine the way such a game would be built. On both sides unless named:

- One shipping profile: fat LTO, one codegen unit, `panic = "abort"`.
- **Bevy's pipelined rendering is on.**
- Bevy is built with only the features each workload needs.
- Each engine uses the faster of its documented ways, measured. Bevy draws
  the sprite rows with `Mesh2d` and a `ColorMaterial`, moves entities with
  `par_iter_mut` and lays out the UI with its CSS grid. Ponko moves entities
  with `par_for_each`.
- rapier's `parallel` and `simd8` features.

  ['Step 10,000 boxes falling into a pile (2D physics)', 3.25, 4.50],
  ['Time to first frame', 26.8, 71.6],

No row changed sides, but Bevy's drawing rows moved a lot. 100,000 sprites
went from 11.6 to 6.74 ms, a million from 105.7 to 58.9 ms, the still UI
from 4.58 to 2.71 ms, and the time to first frame from 199 to 72 ms. Ponko's
drawing rows barely moved, because it has no pipelining to turn on. The
sprite gap shrinks from 10× to 6.6×, and the skinned characters from 1.6×
to 1.3×.

Physics halves on both sides with rapier's `parallel` feature (Ponko 6.39 to
3.25 ms, Bevy 8.11 to 4.50 ms). The solver is the same crate, so the
remaining difference is outside it.

One thing I can't explain: two of Bevy's ECS rows got _slower_ with the
shipping profile, by 3% and 5%, outside their ranges. The code is the same
and only the profile changed. The
[full tuned table](/guide/performance.html#both-engines-tuned) has every
row.

## A Second Machine

One machine is an anecdote. The run-time rows were measured again on
26 November on a Windows 11 desktop: an AMD Ryzen 5 3600 (6 cores), 16 GB
and a Radeon RX Vega, once with DirectX 12 and once with Vulkan. The tuned
table and the build rows were not run there.

A caveat first: another job used this machine on the same day. None was
running when each table started, but single CPU rows moved by up to about
70% between the two tables, so read them with that in mind.

| Workload (ms) | Ponko, DX12 | Bevy, DX12 | Ponko, Vulkan | Bevy, Vulkan |
|---|---:|---:|---:|---:|
| ECS: iterate 1M, one archetype | 0.522 | 1.19 | 0.426 | 0.962 |
| Sprites: 100k moving | 2.91 | 29.2 | 2.48 | 30.2 |
| Sprites: 100k, a different tint each | 2.84 | failed | 2.53 | 90.3 |
| Sprites: 1M moving | 27.9 | 244.6 | 29.1 | 265.0 |
| 3D: 100k moving meshes | 15.6 | 39.7 | 14.8 | 31.2 |
| 3D: 1,000 skinned characters | 9.65 | 15.5 | 8.72 | **8.35** |
| 2D physics: 10k boxes | 26.2 | 34.3 | 25.6 | 31.5 |
| UI: 10k nodes, recolored | 7.40 | 21.8 | 7.05 | 20.9 |

Every frame is slower than on the M4 Max, and the ratios between the engines
are close to the first machine's: 100,000 sprites are 10× on DirectX 12 and
12× on Vulkan, physics 1.3× and 1.2×.

Two rows stand out. Bevy wins the skinned characters on Vulkan, as said at
the top. And Bevy's tinted-sprite program failed all three runs on DirectX 12
with `DeviceLost: Out of memory`, from a material for each of 100,000
sprites; the same program runs on Vulkan. The time to first frame on
DirectX 12 is within noise, because one of Ponko's three launches took
1.34 s against 0.25 and 0.26 s for the others.
[All sixteen rows for both backends](/guide/performance.html#windows-desktop-ryzen-5-3600-radeon-rx-vega-directx-12-and-vulkan)
are in the guide.

## Builds and Sizes

Frame time isn't the only thing you wait for. These are a small game on each
side (Ponko's 2D template and the same game in Bevy), built in a fresh
folder on the MacBook: the median of three clean debug builds and of four
rebuilds.

Bevy's default features include much more than a small 2D game uses: 3D,
glTF, audio formats, animation and picking. That is why the second and third
rows build each engine with only what the game needs. After a one-line change
in `src/main.rs` the two rebuild in 0.29 and 0.32 s, which is close to the
noise.

## The Row That Changed Sides

On 22 November, Bevy won the skinned characters on the MacBook: 3.86 ms
against Ponko's 6.06 ms. It was the one row Ponko lost, so it was the one
worth looking into.

Ponko skins on the GPU: a compute pass poses every corner of every model
before anything draws, and the camera and each shadow cascade then read the
result. That part was sound. The mistake was one dispatch, one bind group and
one vertex buffer _per model_: 1,000 small dispatches a frame, which the GPU
ran one after another. The compute pass took 2.66 ms of a 5.93 ms frame.

Now models of one mesh sit next to each other in shared vertex buffers, and
one dispatch poses up to 512 of them. Three meshes, three dispatches:

| | Before | After |
|---|---:|---:|
| GPU: skinning (compute) | 2.66 ms | 0.032 ms |
| GPU: all passes | 3.83 ms | 1.21 ms |
| CPU: encoding 3,770 draws | 0.86 ms | 0.26 ms |
| Vertex buffer changes a frame | 2,770 | 37 |
| Whole frame | 5.93 ms | 2.31 ms |

The pictures are unchanged: every skinning, shadow and reference-image test
passes as before.

The two engines still trade work differently. Ponko skins each corner once a
frame and reads it in every pass, but records one draw per model and pass.
Bevy skins each corner again in every pass that draws it (five times in this
scene) but draws a whole crowd in a few instanced draws. On the M4 Max and on
DirectX 12, Ponko's trade now comes out ahead. On Vulkan on the Vega, Bevy's
still does, by 4%.
[The guide has the full breakdown](/guide/performance.html#skinned-characters-where-the-frame-goes).

## What These Numbers Don't Say

- **This is not a ranking.** It is sixteen workloads on two machines. A real
  game is a mix that no single row describes.
- **Ponko's side wrote both programs.** The Bevy apps use the APIs Bevy
  recommends, and the README says which and why, but people who know Bevy
  better may see a workload that uses it badly. That is a bug in the
  benchmark, and I'd like to hear about it.
- **Nothing was measured on Linux**, on a phone, or on a low-end laptop.
- **Three runs per engine** is enough to see a 2× difference and not enough
  to trust a 3% one.
- **The frames can't be compared pass by pass on Metal.** Bevy reports no
  GPU pass times there, so only whole frames are compared.
- **The C and C++ API has no rows.** It calls the same engine, but nobody
  has written these workloads in C or C++ yet.

## Run It Yourself

Everything is in the engine's repository. You need Rust and Python 3; the
run-time rows take about ten minutes.

```sh
git clone https://github.com/ponkoengine/ponko
cd ponko
python3 bench/compare/scoreboard.py --runtime    # the run-time rows
python3 bench/compare/scoreboard.py --tuned      # the tuned table
python3 bench/compare/scoreboard.py --builds     # build times and sizes
```

The script writes `bench/compare/results/scoreboard.md` and a JSON file with
every run and the load it was taken under. Add `--machine NAME` to keep your
machine's results in their own folder.

If your numbers disagree with these, or you see a Bevy workload that could
be written better, please
[open an issue](https://github.com/ponkoengine/ponko/issues) with the result
file. The [Performance chapter](/guide/performance.html#ponko-vs-bevy-the-scoreboard)
has every table, the Windows results and the method in full.
